# Проект: Анализ данных о сердечных заболеваниях

## Описание проекта

Проект направлен на решение задачи бинарной классификации для предсказания наличия сердечных заболеваний у пациентов на основе медицинских показателей. Используется датасет Heart Disease с 14 признаками и 303 наблюдениями. Цель проекта — построение модели машинного обучения для ранней диагностики сердечно‑сосудистых заболеваний с последующим развертыванием микросервиса.[file:49dee8b1-0f46-4ef7-8639-10abc2a6650d]

В проекте используются:
- Python, pandas, numpy, scikit‑learn для подготовки данных и обучения модели.[file:49dee8b1-0f46-4ef7-8639-10abc2a6650d]
- MLflow для отслеживания экспериментов и сохранения production‑модели.
- FastAPI + uvicorn для реализации REST‑API микросервиса предсказаний.
- Docker и docker compose для упаковки и оркестрации нескольких сервисов.
- Prometheus для сбора и хранения метрик сервиса.
- Grafana для визуализации метрик и построения дашборда мониторинга.
- Отдельный сервис `requests` для генерации запросов к ML‑сервису.[file:9084394e-eba9-48a8-a932-f67d8f861134][file:3c4434b8-5a0a-4f10-8426-a762c3a3ccaf]

## Разработанный микросервис предсказаний

### Описание сервиса

Создан микросервис на базе FastAPI для выполнения предсказаний моделью машинного обучения. Сервис предоставляет REST‑API endpoint для классификации пациентов по наличию сердечных заболеваний. Вся логика проверки и преобразования признаков вынесена в класс `FastAPIHandler`, чтобы роутер отвечал только за обработку HTTP‑запросов.[file:5f2c30cf-2e36-4df9-bb81-d0f3b98d8c36][1]

### Файлы сервиса

**В папке `services/ml_service/`:**
- `main.py` — основной файл FastAPI-приложения с endpoint’ами (`/health`, `/predict`, `/metrics` и т.д.).
- `api_handler.py` — класс для загрузки модели, проверки и преобразования признаков и выполнения предсказаний.[file:5f2c30cf-2e36-4df9-bb81-d0f3b98d8c36]
- `metrics.py` — определение и обновление пользовательских метрик Prometheus (гистограмма предсказаний, счётчики кодов ответов).[file:858d3fac-e1bf-4672-aef7-0b5434a8a99b]
- `get_model.py` — загрузка модели из файла (например, `/models/model.pkl`) или из артефактов MLflow.[file:41cb67cf-aae0-4f45-ab68-2f6650e3c022]
- `requirements.txt` — зависимости сервиса (FastAPI, uvicorn, scikit‑learn, pandas, numpy, MLflow, библиотеки Prometheus и т.п.).[file:7bf9c00c-3927-4e9e-9a12-c4acb42b20e4]
- `Dockerfile` — конфигурация Docker‑образа ml_service (базовый образ Python 3.10, установка зависимостей, запуск uvicorn).

**В папке `services/models/`:**
- `get_model.py` — скрипт для выгрузки модели из MLflow в локальную директорию.
- `model/` — директория с production‑моделью в формате MLflow.
- `model.pkl` — сохранённый pickle‑вариант модели (устаревший, оставлен как артефакт).

## Сервис генерации запросов (`requests`)

**В папке `services/requests/`:**
- `requests.py` — скрипт, который в бесконечном цикле с случайной паузой от 0 до 5 секунд формирует JSON‑запрос и отправляет его в основной сервис предсказаний (на адрес `http://ml_service:8000/...`, если сервисы запущены через docker compose).[file:85917b79-0714-44a6-a008-64621451d60f]
- `requirements.txt` — минимальные зависимости для сервиса (`requests` и его зависимости).[file:ec797536-981a-4078-bca9-f440d3692e23]
- `Dockerfile` — образ на базе `python:3.10-slim`, установка зависимостей и запуск `python requests.py`.

Сервис используется для генерации нагрузки и проверки работы мониторинга (частота запросов, ошибки 4xx/5xx и распределение предсказаний).

## Сервисы мониторинга: Prometheus и Grafana

### Prometheus

**Папка `services/prometheus/`:**
- `prometheus.yml` — конфигурационный файл Prometheus, в котором задан scrape‑job для сборки метрик с основного сервиса:

```yaml
global:
  scrape_interval: 15s
  scrape_timeout: 10s

scrape_configs:
  - job_name: "ml_service"
    metrics_path: /metrics
    static_configs:
      - targets:
          - "ml_service:8000"
```

Prometheus собирает:
- стандартные HTTP‑метрики (количество запросов, latency, statусы) через `prometheus-fastapi-instrumentator` и `/metrics`;
- пользовательскую гистограмму предсказаний модели и метрики ошибок, определённые в `metrics.py`.[file:7abfd83a-c4eb-4434-8676-e33192b063a2][file:858d3fac-e1bf-4672-aef7-0b5434b8a99b][2]

Веб‑интерфейс Prometheus доступен по адресу: `http://localhost:9090`.

### Grafana

**Папка `services/grafana/`:**
- volume‑директория для данных Grafana (`/var/lib/grafana` в контейнере), чтобы настройки и дашборды сохранялись между перезапусками;
- экспортированный дашборд (`dashboard.json`), который можно импортировать в другой инстанс Grafana.[file:3c4434b8-5a0a-4f10-8426-a762c3a3ccaf]

Сервис Grafana в `compose.yml` описан с образом `grafana/grafana`, пробросом порта `3000:3000` и дефолтным логином/паролем `admin/admin`. Веб‑интерфейс: `http://localhost:3000`.[3]

В Grafana настроен источник данных:
- Prometheus с URL `http://prometheus:9090` (имя сервиса внутри docker‑сети).[2]

## Мониторинг и дашборд

### Уровни мониторинга

В проекте реализованы метрики и графики трёх уровней:[file:3c4434b8-5a0a-4f10-8426-a762c3a3ccaf]

- Инфраструктурный:
  - общее количество запросов к API и скорость запросов в минуту (rate по HTTP‑метрикам Prometheus);
  - распределение кодов ответов (2xx, 4xx, 5xx).
- Прикладной (уровень сервиса):
  - частота запросов к основному endpoint предсказаний;
  - количество запросов с ошибками 4xx и 5xx (на одном графике).[file:858d3fac-e1bf-4672-aef7-0b5434a8a99b]
- Уровень модели:
  - гистограмма значений предсказаний модели (Histogram в Prometheus);
  - агрегированные значения предсказаний (например, среднее за окно времени) — для отслеживания возможного data drift.[file:858d3fac-e1bf-4672-aef7-0b5434a8a99b][5]

### Примеры графиков

В Prometheus и Grafana строятся графики:

- Гистограмма предсказаний модели:
  - на основе метрики `model_prediction_value_bucket` (название зависит от реализации) с использованием `histogram_quantile` или `rate(...)` по корзинам.[5]
- Частота запросов в минуту:
  - по метрикам HTTP‑запросов, например `rate(http_requests_total[1m])` с фильтрами по endpoint/методу.
- Количество запросов с 4xx и 5xx:
  - две линии на одном графике по `rate(http_requests_total{status=~"4.."}[1m])` и `rate(http_requests_total{status=~"5.."}[1m])`.[5]

Скриншоты дашборда добавлены в репозиторий (например, в `docs/`) и кратко описаны в этом разделе (какой график что означает и к какому уровню мониторинга относится).

## Исследование данных


### Исходные данные
- **Размер датасета**: 303 строки, 14 столбцов
- **Числовые признаки**: age, trestbps, chol, thalach, oldpeak, etc.
- **Категориальные признаки**: sex, cp, fbs, restecg, exang, slope, ca, thal
- **Целевая переменная**: target (0 - нет заболевания, 1 - есть заболевание)


### Описание признаков:
- age: возраст в годах
- sex: пол (1 = мужской; 0 = женский)
- cp: тип боли в груди
- trestbps: артериальное давление в покое
- chol: уровень холестерина в мг/дл
- fbs: уровень сахара натощак > 120 мг/дл
- restecg: результаты электрокардиографии в покое
- thalach: максимальная достигнутая частота сердечных сокращений
- exang: стенокардия, вызванная физической нагрузкой
- oldpeak: депрессия ST, вызванная физической нагрузкой относительно покоя
- slope: наклон пикового сегмента ST при физической нагрузке
- ca: количество основных сосудов (0-3), окрашенных флюороскопией
- thal: нормальный; фиксированный дефект; обратимый дефект
- target: наличие сердечного заболевания (0 = нет; 1 = да)

### Сохранённые артефакты:
- модель, сигнатура, входные данные, файл MLmodel

**Примечание:** в ранних версиях проекта была проблема совместимости версий Python и scikit‑learn между средой обучения модели (Python 3.10 + конкретные версии библиотек) и Docker‑контейнером. Это приводило к ошибке загрузки модели в контейнере. В актуальной конфигурации для ml_service используется базовый образ `python:3.10-slim` и версии зависимостей, совпадающие с окружением обучения модели, что устраняет конфликт и позволяет корректно загружать модель внутри контейнера, но доступ к дашборду все равно невозможен. Модель требует переобучения с совместимыми версиями зависимостей.
